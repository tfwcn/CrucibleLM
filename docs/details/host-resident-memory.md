# 宿主记忆：逻辑留 GPU，记忆留 CPU

> 一句话：把 Engram 表的主副本放在主机内存，前向只把**命中的行**搬上卡，
> 反向只把**命中行的梯度**搬回主机，用**行稀疏 Adagrad** 只更新那几行——
> 显存占用与表规模解耦，数学一点不改。

## 痛点

Engram 的价值在于"表可以很大"：`orders × heads × slots × d_head`，
16M 行 × 8 头 × 3 阶的 FP8 表就是十几 GB。可 16 GB 的卡上，
模型权重 + 激活 + KV 已经把显存吃干，**记忆表是第一个被挤掉的东西**。

另一边，这类表有三个性质，说明它**不该**和稠密权重享受同等待遇：

1. **稀疏访问**：每 token 每表只查 1 行，一个 step 命中率通常 <1%；
2. **无算术**：查表是纯内存搬运，没有 FLOPs，GPU 的算力对它没用；
3. **行独立**：行与行之间没有跨行运算（对比 Sinkhorn 的列归一化），
   更新天然可以按行做。

所以问题不是"能不能放 CPU"，而是"放过去之后，每步要付多少搬运费"。
这篇文档先用基准把搬运费量出来（Step 0），再按量出来的数选方案。

## 直觉：把"算"和"记"分开

GPU 擅长的是**每个字节都被算很多次**的数据（权重矩阵、激活）。
记忆表相反：一个字节被读一次，然后立刻参与一次乘加就丢掉。
把它放在显存里，等于用最贵的存储放最不划算的数据。

反过来，CPU 内存便宜 32~64 倍、容量大一个量级，但**串行**——
一次随机 gather 就是一次 cache miss。所以"表放 CPU"的代价曲线是：
**随命中行数线性增长，与表大小无关**。这正是我们想要的形状。

## 调研：这件事别人做到哪一步

| 工作 | 做法 | 对我们的意义 |
|---|---|---|
| **Goodfire K-FAC 曲率分离**（2510.24256） | 把优化器的曲率统计与权重分设备存 | 状态可以分设备，但**稠密权重的更新**仍要整块参与，搬不动 |
| **记忆/推理解耦**（ACL2025, 2411.13504） | 记忆用检索外挂，推理只留小模型 | 记忆本来就该是可替换、可离线的 |
| **Meta Memory Layers**（2412.09764） | 可训练的键值记忆层，稀疏激活 | 表是"产品级"组件，规模要能独立于主干扩 |
| **DeepSeek Engram**（2601.07372） | n-gram 哈希表 + 上下文门控 | 本项目已实现；表更新走 Sinkhorn（**全表**归一化，见下） |
| **KTransformers**（SOSP'25） | MoE 专家留 CPU，按路由搬 | 已验证"稀疏访问 + 按需搬运"在推理侧可行 |
| **MoE-Infinity / LLM in a flash** | 专家/权重落盘 + 页缓存预取 | 磁盘层的前提是**访问局部性**，冷读延迟决定下限 |
| **TorchRec / FBGEMM** | embedding 表放 CPU，行稀疏 SGD/Adagrad | 训练侧的标准答案：**梯度也必须稀疏**，否则等于搬全表 |

结论：**推理侧**早已是工程常识，**训练侧**的关键只有一条——
**反向和优化器都不能碰全表**。只要有一条路径会 materialize 全表梯度
（`index_select` 的 autograd 反向就会 `zeros_like(weight)`），
"表留 CPU"就退化成"每步把全表搬一遍"，收益归零。

## 硬件基准（Step 0：先量，再写代码）

脚本 `scripts/bench_mem_tier.py`，报告落 `data/bench/`（已 gitignore）。
本机：RTX 3080 Laptop 16 GB / i7-11800H / RAM 16.6 GB / `/dev/sdd`。

阈值是**动手前定死**的，避免事后找理由：

| 判据 | 阈值 | 含义 |
|---|---|---|
| H2D 4 KB pinned 端到端 | < 30 µs | 与一次 kernel launch 同量级，可藏进计算 |
| 磁盘 4 KB QD=1 p50 | < 200 µs | 一次随机读能藏在 1 ms 级算子后 |
| 宿主表 gather（4096 token/步） | < 5 ms | 相对单步百 ms 级可接受 |

### 实测

H2D（逐次 event 计时会被分辨率噪声抬高，**批量摊销**才是可信值）：

| 大小 | pinned | 批量摊销 | 端到端（含 Python 下发） | 等效带宽 |
|---|---|---|---|---|
| 4 KB | 是 | **8.0 µs** | 10.1 µs | 0.41 GB/s |
| 64 KB | 是 | 23.9 µs | 33.5 µs | 1.95 GB/s |
| 1 MB | 是 | 128.1 µs | 150.6 µs | 6.96 GB/s |
| 8 MB | 是 | 1006.1 µs | 1106.7 µs | **7.58 GB/s** |

判读：小块的成本是**固定开销**（launch + 同步），不是带宽；
真实链路约 7.6 GB/s（笔记本 3080 走 x8），8 MB 才吃满。
一 step 预填 4096 token 只搬 ~3 MB，理论上 0.4 ms 级。

宿主表 gather（1M 行 × 32 列 FP8，4096 token × 3 阶 × 8 头 = 98304 行）：

| 项 | p50 |
|---|---|
| CPU 随机 gather | 0.41 ms |
| 汇聚到 pinned 缓冲 | 0.13 ms |
| H2D（3.15 MB） | 0.56 ms |
| **合计** | **1.10 ms** |

判读：**CPU gather 和 H2D 各占一半**。前者不随 GPU 变快，是"表留 host"
最容易被低估的一项；后者证明 3 MB 级搬运确实是亚毫秒。

磁盘随机读（O_DIRECT 绕页缓存，2 GB 文件）：

| 块大小 | QD | IOPS | MB/s | p50 | p95 |
|---|---|---|---|---|---|
| 4 KB | 1 | 6375 | 26 | **143 µs** | 236 µs |
| 4 KB | 8 | 22710 | 93 | 211 µs | 421 µs |
| 256 KB | 8 | 16631 | 4360 | 355 µs | 540 µs |

mmap 页缓存（抽样 20000 页，先 `fadvise(DONTNEED)` 只丢本文件的缓存）：

| 项 | 值 |
|---|---|
| 冷遍每页 | 63.9 µs（readahead 摊薄了单页成本） |
| 热遍每页 | 0.21 µs（≈ 内存速度） |
| 冷/热比 | **304×** |
| 冷遍块设备读量 | 2146 MB（≈ 2.1 GB，预读放大约 1.07×） |

判读：盘不是完全不能用（143 µs 过阈值），但**热行必须被页缓存兜住**；
一旦工作集超过可用内存，落盘表就退化成"每次前向都等盘"。

**结论：A 档（表留 host + 按需搬行）可行，C 档（表落盘）在守住热集的前提下可行。**

### 端到端（真机冒烟：`scripts/smoke_engram_host.py`）

基准只量了"搬运要多少钱"，还要确认三件事：语义没变、表真的不在卡上、
单步代价多大。脚本建一个 2 层的小模型（每 2 层插 1 个 Engram，2 阶 × 4 头 = 8 张表/层），
batch 4 × seq 128 = 512 token/步，`sinkhorn=True`，两个变体**分进程**测显存：

| 表规模 | 变体 | GPU 参数 | 稳态显存 | 训练峰值 | 单步 |
|---|---|---|---|---|---|
| 64 MiB（65,521 行/张） | 设备表 | 68.8 MiB | 154.0 MiB | 242.7 MiB | 183–204 ms |
| 同上 | **宿主表** | **4.8 MiB** | **26.0 MiB** | **79–86 MiB** | 188–196 ms |
| 256 MiB（262,139 行/张） | 设备表 | 260.8 MiB | 538.0 MiB | 878.7 MiB | 241.0 ms |
| 同上 | **宿主表** | **4.8 MiB** | **26.0 MiB** | **79.1 MiB** | **184.2 ms** |

三条读得出来的结论：

1. **语义没变**：同权重同输入下 `max|Δ logits| = 0`（逐位相同），
   训练前 loss 完全一致（5.5753 vs 5.5753）。分设备只改搬运，不改数学。
2. **显存与表规模解耦**：GPU 参数恒为 4.8 MiB（表全在 CPU），稳态省下的
   128 MiB / 512 MiB = **表 + 它的 Sinkhorn 动量**（两份都是表大小）。
   表再翻 4 倍，省下的也翻 4 倍，而 GPU 侧一字节不涨。
3. **时间不一定亏**：64 MiB 表时两者持平（±3%，噪声内）；
   256 MiB 表时宿主表**反而快 23.6%**——因为 Sinkhorn 每步要对**全表**做 22 趟
   行列归一化（代价随表线性涨），行稀疏 Adagrad 只碰命中行（代价与表大小无关）。
   表越大，"省显存"和"省时间"是同一个方向。

> 注意：这条对比是"行稀疏 Adagrad vs Sinkhorn"的对比，不是纯搬运开销的对比。
> 想要纯搬运账单，看上面第 2 节的 gather + H2D（≈1.1 ms/4096 token）。


## 三条路线与选型

| 档 | 做法 | 代价 | 采用 |
|---|---|---|---|
| A | 主副本留 CPU，按需搬命中行，反向只回传命中行 | PCIe + CPU gather（~1 ms/step @4096 token） | ✅ 本次实现 |
| B | 表留 CPU 且 prefill 整块搬、decode 单行搬 | 复杂度翻倍，收益在高并发推理 | ❌ 先不做 |
| C | 表落盘 + mmap + 页缓存兜热行 | 依赖访问局部性与可用内存 | 🔶 基准已留数据，未接线 |

选 A 的理由：它是唯一**训练/推理都能用同一份实现**的档位，
而且把"记忆不占显存"这件事做到了极致（表在 16 GB 之外还能再扩）。

## 原理：为什么"表搬走"不改数学

前向对每个 `(阶, 头)`：

```
idx  = hash(gram) % rows               # 整数哈希，CPU/GPU 逐位一致
e    = Table[idx]                      # 只取命中行（CPU 随机 gather）
e   ↑ 拷到 GPU（仅命中行）              # H2D
e    = fake_quant_fp8(e)               # 与表在 GPU 上时同一个算子
```

因为 `fake_quant` 是**按行**量化（scale 只在本行 16 通道内取），
"先搬行再量化"与"先量化再取行"逐位相同。所以表的物理位置**不在数学里**，
只在数据搬运路径里——这就是单测 `test_lookup_host_matches_dense` 卡的东西。

反向不一样。`F.embedding`/`index_select` 的 autograd 反向会先
`zeros_like(weight)` 再散射，等于每步物化一整张表的梯度（1M×32 × 4 B = 128 MB，
16M 行就是 2 GB）。所以宿主表**不能走常规 autograd**，要用自定义 Function
把梯度塞进旁路队列：**只有命中行**进队列，优化器也只更新这些行。

## 从想法到代码

```
# engram.py
class _HostGather(Function):
    forward(idx_cpu, weight, sink, device, dtype):
        rows = weight.index_select(0, idx_cpu.reshape(-1))   # CPU 随机 gather
        return rows.to(device, dtype).view(*idx.shape, cols)  # 只搬命中行
    backward(grad_out):
        sink.append((idx, grad_out.to("cpu", fp32)))          # 只回传命中行
        return None                                            # 绝不产生全表 grad

# EngramTable
_apply(fn):                # model.to(cuda/bf16) 时
    if host: return self   # 主权重不动（这才是"不占显存"）

# optim.py
class SparseRowAdagrad:
    step():
        uniq = unique(cat(idx))              # 一步内同一行多次命中先求和
        upd  = acc / (sqrt(Σg²) + eps)
        weight[uniq] -= lr * upd             # 只碰命中行
```

接线只有三处：`EngramMemory._embed`（`ids` 一次性搬 CPU，24 张表共用一次 D2H）、
`build_block`（`engram_host` 透传）、`CombinedOptimizer`（宿主表从 Muon/Adam/Sinkhorn
组里**排除**，交给 `SparseRowAdagrad`）。

## 实现细节

- **索引在 CPU 上算**：`ids` 每层搬一次 CPU，24 张表的哈希全在 CPU 算。
  否则每表一次 D2H 同步 = 24 次同步/前向。哈希全是 int64 的乘加与掩码，
  CPU/GPU 逐位一致（无溢出），所以不影响数值。
- **两端 dtype 对齐**：宿主表主权重保持 fp32（不跟随 `model.to(bf16)`），
  输出时按主干 `w_v.weight.dtype/device` 转换——`lookup(idx, device, dtype)`
  的三个参数就是干这个的。
- **`_apply` 早退**：`nn.Module.to()` 会遍历子模块调 `_apply`；宿主表直接返回
  `self`，连打包缓存 `w8/s8` 也不搬（推理时要的就是 host 存储）。
- **梯度累积天然支持**：`_grad_sink` 是列表，多个 micro-batch 的 `(idx, grad)`
  依次入队，一次 `step()` 去重求和 → 与"先累梯度再 step"等价，但不占全表内存。
- **`zero_grad` 必须清队列**：否则跳过的 step 会把上一次的行梯度重复消费。
- **打包（推理）也走后端**：`pack()` 在 CPU 上量化，`w8/s8` 留 host，
  取行后 `to(device)` 再反量化，与未打包逐位一致（1.06 B/通道 × 行数）。

## 代价与边界（写在前面）

1. **优化器口径变了**：宿主表不进 Sinkhorn（全表 22 趟归一化在 CPU 上几百 ms，
   等于用时间把显存换回去），改走**行稀疏 Adagrad**。这不是"等价替换"，
   是**换了一种更新规则**——所以默认关、续训须删 `optim.pt`（与切换优化器同一条坑）。
   `lr` 也是 Adagrad 口径（默认 0.03），和 Adam 的 3e-4 不可直接比。
2. **状态仍是一整张表**：Adagrad 累加器惰性分配但按全表形状（fp32 = 1× 表大小）。
   16M 行 × 32 列 = 2 GB host 内存——省的是显存，不是内存。
3. **prefill 的 gather 是串行的**：0.41 ms/98304 行 ≈ 4 ns/行，看起来很快，
   但它是**单线程 CPU 时间**，会和 dataloader/其他 host 工作抢核。
4. **decode 路径不吃亏**：单 token 只查 24 行，H2D 4 KB 级，pin 住后 ~8 µs，
   相对一次 decode 的算子时间可忽略。
5. **不能和"整表搬"混用**：`model.to(device)` 之后再手动 `table.weight.to(cuda)`
   会让 `_apply` 的早退失效，表就回显存了（单测锁死 `to("cuda")` 后仍在 CPU）。

## 什么时候不该用

- 表小到能塞进显存（< 显存的 10%）：搬运费纯亏，直接放卡上；
- 高吞吐小 batch 推理：CPU gather 会变成瓶颈，不如卡上查表；
- 需要 Sinkhorn 的表间列归一化语义（例如 embedding 与 head 共享列分布）：
  行稀疏 Adagrad 没有列信息，别拿它替代。

## 坑

- **`index_select` 的 autograd 反向会物化全表梯度**——这是"表留 CPU"最容易踩的坑，
  也是必须自定义 Function 的原因（见 pitfalls）。
- **不要逐表 `.to("cpu")`**：一次前向 24 张表 = 24 次同步，prefill 直接慢一个量级。
- **`/proc/self/io` 在容器里可能不存在**：基准改用 `/sys/block/<dev>/stat` 的读扇区计数。
- **O_DIRECT 要 4 KB 对齐**：offset、长度、缓冲区三者都要对齐，缓冲区用
  `mmap(-1, size)`（页对齐）最省事；稀疏文件读洞不走盘，会测出假快。
- **mmap 冷缺页带 readahead**：单页均摊成本比 O_DIRECT 低，但 I/O 总量被放大，
  表变大后这个便宜会消失。
- **`fadvise(DONTNEED)` 只丢本文件的页缓存**：做冷热对比时用它，别去动全局
  `drop_caches`（会影响同机其他进程）。
