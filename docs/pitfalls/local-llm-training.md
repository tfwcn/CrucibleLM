# 本地小 LLM 训练三坑（`src/llm/local` 实战教训，RTX 3080 Laptop 16G）

## 1. 短卷积必须严格因果（loss 虚假塌到 ~0 的元凶）

`GatedDeltaLite` 的 K/V 短卷积若用 `padding=1` 双边补零，输出位置 `i` 会看到
输入 `i+1`——而自回归训练的目标恰是下一 token，等于把答案抄给模型。
模型会逐渐把全部容量转到复制通道：

- loss 加速塌到 ~0.1（复制通道越学越依赖，正反馈）
- 留存集同样沦陷（复制对任何数据有效，不是过拟合）
- 生成变复读机（推理时没有标准答案可抄）
- 随机 token 对照组短期纹丝不动（通道隐蔽，几十步内发现不了）

修法：`padding=0` + 左补 `(kernel-1)`（见 `_causal_conv`）。
回归单测：`tests/test_train_flow.py::test_linear_attn_causal_no_future_leak`
（改输入位置 `i`，断言输出 `<i` 纹丝不动）。

教训：任何"近似因果"（ asymmetric pad、单边截断验证）都不允许进训练路径；
凡是新加的序列混合操作，先写因果性单测再训。

## 2. `generate()` 必须恢复 train/eval 状态（OOM 真凶）

`generate()` 开头 `self.eval()` 后若不恢复，训练循环中穿插一次采样，
之后所有训练步都被静默关闭梯度检查点（开关条件是 `self.training`），
9 个线性层的 O(N²) 注意力矩阵同时驻留，16G 直接 OOM。
崩溃点恰是采样后的第一个训练步，极具迷惑性。

修法：`generate()` 包 `try/finally` 恢复之前状态（见 `_generate_inner` 拆分）。
回归单测：`test_generate_restores_train_mode`。

## 3. 本地爬取语料必须 block 级 shuffle（loss 台阶跳变）

parquet 按爬取顺序存（相邻文档同站点同模板），本地流若不打乱，
模型一个站点一个站点地学，换站点 loss 跳变。
`ShuffleBuffer`（默认 512 块蓄水池，`--shuffle-buffer` 可调），只包训练流，
评测流保持确定性。HF 流式虽有文档级 shuffle，打包拼接仍保留局部顺序，
同样走这一层。

## 4. 短卷积解码必须缓存左文（训推 k/v 对不上）

K/V 短卷积（kernel=3）让位置 `i` 的 k/v 依赖输入 `i-2..i`。
解码每步只喂 1 个 token，若直接卷积，左感受野全是零，与全前向算出的 k/v
不一致——生成质量系统性受损，且写法上极易漏（单测必须覆盖
prefill+单步解码 vs 全前向逐位一致）。
修法：past 里加 `(k_buf, v_buf)`（Mamba 系 `conv_state` 同理），
`_step_conv` 统一处理全序列/单步两种形状，尾部恒 `(k-1)` 长。

**尾巴要取 `buf + current` 的末段，不是只取 `current`。** 若在拼接 `buf` 之前
截尾，单步解码时 buf 每步都被"左补零"覆盖成 `[0, x_t]`，从第 3 个 token 起
左感受野丢一个真实 token：S 状态偏差可达 1.9（量级同 S 本身），逐位置输出偏差
0.1~0.4，看起来"像随机噪声"而不是 bug，很容易误判成数值精度问题。
判据：prefill 一次拿到的 conv 尾部，必须等于逐 token 解码同样步数后的尾部。

## 5. 线性注意力所有分支的 scale 必须一致

并行分支 scores 自带 `×scale`，串行/解码/分块的 `q^T·S` 形式必须显式补上，
漏掉就是全局 √d 倍的输出偏移，经 norm/router 非线性放大后训推分叉。
凡新增注意力计算路径，一律跑"与并行分支逐位一致"单测。

## 6. SSE 无长度响应必须显式关连接

`text/event-stream` 响应既无 Content-Length 又无 chunked 时，
`Connection: keep-alive` 会让"读到 EOF 为止"的客户端（urllib 的 `read()`、
部分 SDK）永远等待。教训：SSE 写完 `[DONE]` 后置
`handler.close_connection = True`；单测必须按真 SSE 客户端写法
（增量读到 `[DONE]`），而不是 `read()` 一把梭——后者测不出 framing bug，
还会把 framing 问题伪装成"偶发 hang"（时好时坏极具迷惑性）。

## 7. 解码路径手拼 block 前向时，新加的子层必须同步跟进

`model._decode_step` 为复用逻辑手拼了 `attn+moe`（省一次 block 调度），
记忆层加进 `HybridBlock`（MoE 之后）时解码侧漏跟：零初始化阶段恒等看不出，
value 训出非零后增量解码与全前向分叉约 0.69（logits 量级）。
教训：凡在 block 里加子层，同步改 `_decode_step`，并加"value 非零后
prefill+解码 vs 全前向逐位一致"单测——恒等起点的模块，bug 只在训出
非零后现形，默认的恒等单测盖不住。

## 8. 贪心解码必配重复惩罚（高频 token 循环吸引子）

SFT 模板标签（`<用户>`）和 markdown（`####`）里的 `<`、`#` 是超高频 token，
贪心解码稍一犹豫就掉进循环吸引子（`<<<<…`、`高糖×30`），且与训练步数无关
（三档权重 `<` 占比一模一样 0.125）——"300 步后变瓢"第一眼像过拟合，
8 个 prompt 一铺开才发现 200 步也一样瓢，只是 sample prompt 恰好是最会背的一题
（幸存者偏差）。修法：`_sample_next` 加 HF 语义 repetition_penalty
（已出现 token 正 logit 除、负 logit 乘），贪心配 1.2~1.4，
实测 4-gram 复读 0.58→0.04；服务侧 `repetition_penalty` 参数透传。
判据：固定 prompt 集 × 多档权重，`<` 占比 + 4-gram 复读率双降才算修好，
别只看 sample 那一题。

## 10. micro 循环必须以 accum 个数为终止主条件（数据耗尽只做辅条件）

把 `for micro_i in range(accum)` 重构成 `while pending is not None`
（为塞检索前瞻）后，单目录小数据冒烟全过——因为 1 个文档秒耗尽、
`used==0` 正常退出；一上 50 万对的混合数据直接转几千个 micro 不停
（CPU 700% 烧 15 分钟，faulthandler 抓栈显示在正常 forward 里空转，
极具迷惑性）。教训两条：一是终止条件重构必须保持原语义
（个数主条件 + 耗尽辅条件，双条件缺一不可）；二是 CPU 冒烟必须含
"耗不尽"的大数据用例，只测小数据等于没测（见 test 里的 mix 冒烟备注）。

## 9. torch.compile 在增长缓存上越编越慢（删掉的教训）

`_decode_step` 每步约 1800 个小算子，看似 compile 的天菜，实测 eager 22.5
→ compile 5.1 tok/s（更慢）。两道墙：
1. cudagraphs（reduce-overhead）要求静态内存，MLA latent/卷积尾每步 `cat`
   增长，抓图即炸；
2. dynamic=True 也救不了：dynamo 把每层 attn 拆成子帧，符号形状没传进去，
   `past[i] size mismatch` 逐层每步重编（recompiles 日志刷屏）。
结论：先静态缓存（预分配、按位写，不再 `cat` 增长，涉及 mla/sparse 两处
decode），再谈 compile；顺序反了就是负优化。这条是"本地无效不进库"活例子：
方法写完、单测全绿、真机一测变慢——删了，只留教训。
后续：静态缓存落地后 compile 复活（`model.compile_decode()`），sparse 的
`select_keys` 纯 Python 集合逻辑标 `@torch._dynamo.disable`（eager 跑、
不重编；输出形状恒定，下游不断）——30.9 tok/s。
附带实测：MoE 分组 bmm（16 次 dispatch→3 次）13→22.5 tok/s，真提速，已留；
bf16 推理同速（launch-bound 下带宽不是瓶颈）但显存减半，200K 长上下文有用，
`LocalChatBackend.load(..., dtype="bf16")`，已留。

## 11. 多 token 增量解码：补块内因果 + 与单步同算术（投机验证的隐性依赖）

投机解码的并行验证会一次喂 t 个 token，触发各注意力层此前只在 `t==1` 下用过的
"带 past 解码"路径。两处会静默出错：

1. **块内因果缺失**：MLA 解码掩码原来只屏蔽"预留空位"（`keys < pos+t`），没屏蔽
   同批未来的 token——`t>1` 时新查询会偷看同批里更靠后的草稿位置。修法：
   `_valid_mask` 在 `t>1` 时补 `keys <= q_pos` 的因果项；`t==1` 时该式退化为旧式，
   逐位不变（单测 `test_mla_multi_token_decode_is_causal`）。
2. **算术不一致**：验证路径若与逐 token 解码的浮点顺序不同，主干"验证出的贪心"
   会在近并列 logit 上与真贪心分叉，破坏"输出=贪心"的契约。修法：线性层 `t>1`
   分支按单步同款递推（初值 `s_prev`，不图并行）；稀疏解码取最后 t 个查询
   （`start=total-t`，块内由 `chunk_causal_mask` 保证因果）。
   凡新增"能一次解码多 token"的路径，一律加"与逐 token/全前向一致"回归单测。

## 12. 专家 offload 必须逐个 ensure，不能整批

`_forward_offload` 最初一次性 `ensure(命中的全部专家)` 再统一算。当
`offload_capacity < 命中专家数` 时，后搬入的专家按 LRU 把先搬入的挤回冷端
（disk 目标下参数被置 meta），随后用到这些"已置 meta"的专家 → 输出错乱
（实测偏差 0.33，量级同正常输出，极像精度问题）。修法：在逐专家循环里
**用前逐个 ensure**；单测用 `capacity=2/3`（小于命中数）覆盖。
教训：LRU 淘汰与"正在使用的对象"必须解耦——先 ensure 再用的前提是容量够，
容量不够就必须"取一个用一个"。

## 13. 投机解码的部分接受：用"按步缓存"跳位，别逐 token 重放

部分接受草稿后要把状态挪到"已提交前缀末位"处。最初实现是"回退到本轮起点 +
逐 token 重放前缀"，每次拒答要多付**一整步前向**（实测占轮时 ~20%，吞吐
1.29x→1.45x 就是省掉它）。改法：让 `_decode_multi` 顺手返回 `step_pasts[i]`
（"提交前 i+1 个 token 后"每层的完整缓存），转入下一轮时直接
`h = h_multi[:, A]`、`pasts = step_pasts[A]`，**零重放**：

- 线性层的多 token 分支本来就在按步递推，顺带把每步 `(s_i, k 尾, v 尾)` 记进
  `multi_steps`（卷积尾就是原始投影序列的定长切片，见 `linear_attn.py`）；
- MLA/稀疏复用同一缓冲（`index_copy_` 原地写，已含全部 t 个位置），只需把
  `pos` 指回 `pos+A+1`，越界处由掩码屏蔽；
- **坑**：`t==1`（本轮无草稿）不会走多 token 分支，`multi_steps` 不更新——必须
  单独把 `step_pasts` 特判为 `[new_pasts]`，否则会读到 `None`。
- 契约由 `test_decode_multi_step_pasts_match_sequential` 锁定：从 `step_pasts[A]`
  续跑必须和从头逐 token 跑到 A 的续跑逐位一致。

## 14. hybrid 起草别把 MTP 猜测并进上下文喂 ngram（后缀检索被污染）

`hybrid` 最初是"MTP 给第 1 位，再把 `上下文+MTP猜测` 喂 ngram 补后续位"。结果
ngram **几乎永不命中**：ngram 从最长后缀往短找，而最长的那个后缀现在以"没见过的
MTP 草稿"结尾，任何长度都匹配不上历史。实测 hybrid 退化成纯 MTP（每轮恒 1 个候选）。
修法：**只在 ngram 与 MTP 首猜一致时**才采纳 ngram 的更长续写，否则只用 MTP 单猜。
教训：多来源起草要各猜各的、再按"一致性"融合，别把一家的猜测当上下文去喂另一家。

## 15. 磁盘 offload 的落盘文件名必须每个 store 唯一（多层共用目录会互相覆盖）

`ExpertStore` 落盘路径最初恒为 `{offload_dir}/expert_{i}.pt`，**不含层标识**。而
`setup_offload` 为每一层各建一个 store，却共用同一个 `offload_dir`——于是后建层
把先建层的专家文件逐个覆盖，且只在"磁盘 prefill 前"读回时才暴露：`prefill` 过后
权重已被换成别层的专家，输出偏差 0.15（量级同正常输出，极像精度问题）。CPU 目标
不受影响（专家存内存、各 store 各自持有引用），所以只测 CPU 的端到端用例照不出这个坑。
修法：`ExpertStore` 加 `name` 前缀，`setup_offload` 传 `layer{li}`。
教训：**凡是"多个实例写同一目录"的持久化，文件名/命名空间必须区分实例**；
端到端回归要覆盖每一种 target，别只测最省事的那种。

## 16. 预取只填空位、绝不淘汰（否则挤掉工作集，搬运数暴涨）

LES 预取最初走的是普通 `ensure`，会和真实使用一样做 LRU 淘汰。结果：预取把
"下一步马上要用的专家"按 LRU 挤回冷端，紧接着真实使用又要搬回来——实测
（16 专家、top_k=4、`les_topn=4`、`capacity=8`）搬运数翻 3 倍（~1.2 万→~3.7 万）、
吞吐减半（~6.7→~4.7 tok/s）。修法：预取在容量满时**不淘汰工作集**——只回收
"预取但从未被真正命中"的专家（投机占位，可随时丢弃）；没有可回收的就直接跳过，
淘汰权只留给"真正要用专家"的那一步。
教训：**预取是"锦上添花"，必须保证它不会破坏当前工作集**；任何"提前做"的优化
都要论证它不会和"正在做的事"争资源。

## 17. 异步预取必须配 pinned 源 + event 等待，且容量按"驻留集"计

把预取搬到独立 CUDA stream 上有三个坑，缺一个就出错或无效：

1. **源必须 pinned**：非 pinned 的 H2D 拷贝会阻塞 host 线程，`with stream` 也
   退化成同步——异步化为零。故 `_cold` 主副本一律 `.pin_memory()`。
2. **必须 event 等待**：side stream 上的拷贝与默认流无序。正常 `ensure` 命中
   预取来的专家时，要 `torch.cuda.current_stream().wait_event(ev)` 再用模块参数，
   否则读到未写完的权重（数值随机错，不报错）。
3. **容量按 `_resident` 计，不是 `_hot`**：预取进的专家不进 `_hot`（不扰动工作集
   LRU 时序），若容量只数 `_hot`，预取会绕过上限把显存撑爆。
   另需 `_resident` 命中即跳过 `_load`，否则"预取来的 + 正常 ensure 的"同一专家
   被搬两次。

教训：**"异步"不是加个 `with stream` 就完事**——源内存、同步原语、容量口径
三件套要对齐，否则要么没异步、要么静默错误。

## 18. 异步预取在真实模型上中性偏负；且"回收预取未用"会引发 churn

实现异步预取后实测（真实 128M、RTX 3080 Laptop、`bench_offload_les.py`）：预取在
各容量下比同步 offload 略慢 0.05–0.11x；根因是 offload 的代价主要来自"逐专家
dispatch"（分组 bmm 用 3 次 bmm 替 16 次逐专家），而单专家 ~1.8MB、H2D 拷贝极快，
异步重叠省不到什么，反倒多搬了"预测但没用"的专家。

更要命的是**允许预取"回收预取未用空位继续预取"**：容量=12（宽裕）时形成
"预测→搬入→没用→回收→再预测"的 churn，搬运 173→9382、吞吐恶化到 2.28x。
修法：**预取只填空槽、绝不淘汰任何专家**——既不掉工作集，也不回收预取未用。
改后搬运 173→218，churn 消失。

教训：
- **预测类优化必须先验证"预测质量"，并认清瓶颈在哪**——瓶颈是 dispatch 而非搬运时，
  异步预取只是添乱；
- **"回收投机占位"看似无害，实则会自激**：任何"提前做 + 满了就回收再做"的循环都要
  先论证不会形成 churn，否则越勤快越亏；
- 异步/预取类开关默认关，给出量化门槛（offload 是"省显存才能跑"的刚需 + 路由可预测）
  再谈收益。


## 19. 记忆/门控层里的短卷积同样是"有状态"的（Engram 解码对不上全前向）

第 4 条讲过短卷积解码要缓存左文。Engram 条件记忆又踩了同一个坑的变体：论文把
短卷积作用在**门控后**的 `Ṽ=α⊙V` 上，而 α 依赖各位置的 hidden。逐 token 解码时
手上只有当前 hidden，卷积感受野里的历史值拿不到——于是"prefill+逐 token 解码"
与"整段一次前向"数值对不上（实测 last-position diff ~0.1，纯贪心输出分叉）。

修法不是给 Engram 也接一套跨步卷积状态（那要动 `_decode_step`/`_decode_multi`
的按步缓存切片，面很大），而是**换位置**：把短卷积放在门控**之前**，作用在仅由
token id 决定的 `V=W_V e` 上。这样感受野内全部只依赖 id，解码每步只需窗口内
`lookback = (kernel-1)*dilation + max_order - 1` 个历史 id，**无跨步状态**，
`_decode_step`/`_decode_multi` 只要把这段上下文 id 传进去即可。代价是少了一层
"对门控信号做卷积"（与论文不完全等价，已在 details 文档写明）。

教训：
- **凡是时序卷积，先问"它的输入是不是只依赖 id"**：只依赖 id → 用窗口 id 现算，
  无状态；依赖 hidden → 必须缓存卷积尾（第 4 条）。
- 取巧换位置时要把"与原文不等价"写进 details，别让后人以为复刻了论文。

## 20. 跨层共享缓存：prefill 与 decode 的取用方式不同，两处都要接

CSA2 让 Reuse 层借最近 Full 层的 latent。写的时候发现一个容易漏的点：

- **prefill/训练**时 Reuse 层自己的 `past=None`，必须显式把 Full 层刚算出的 latent
  经参数传进来，它才能出 K/V；
- **解码**时情况反过来了——`_prefill` 已经把 Reuse 层的缓存对象**共享成和 Full 层
  同一块张量**，Full 层每步 `index_copy_` 写进去后，Reuse 层读到的就是最新值，
  它只需"跳过写入"（`write=False`），根本不用再传参数。

于是同一个"复用"在两条路径上是两种接法：prefill 靠传参，decode 靠对象别名 +
写开关。**只接一处会得到"训练对、解码错"**（或反之），而且零初始化/单步时未必暴露。
教训：
- 共享可变缓存时，先想清楚"谁写、谁读、顺序如何"——Full 层必须排在它服务的
  Reuse 层之前（本实现按层序天然满足）；
- 对象别名会让"传参"看起来多余，但只对 decode 成立，prefill 没有共享源，别一概而论；
- 判定单测要覆盖 `prefill+逐 token 解码 == 全前向`、`_decode_multi == 逐 token`，
  两条路径都过才算接对。

## 21. 哈希记忆的收益前提是"上下文重现"，不是"加了容量就有用"

Engram 接完、单测全绿、恒等起点也锁定后，本以为剩下就是训练的事。实测打脸：

**现象**：从真实 128M 权重（ckpt-005300）续训，`engram_every=4`（层 0/4/8，表 8191）
对基线跑了 600 步（2.46M token），`val_loss` 两条曲线几乎重合——差值全程在 ±0.001
内，末尾 4.3133 vs 4.3133。即**统计上无效果**。

**但模块没坏**（先排除"没接上"）：训练后 `||W_V||≈0.34`（已从零长出来），把 `W_V`
置零（→输出恒 0、回到恒等）前后，logits 变化 `max|Δ|≈1.22`、argmax 翻转 1.5%。
所以记忆确实在改输出——只是改的是**噪声**，不是信号。

**根因在优化器动量里看得最清楚**：翻 `optim.pt` 的 state，Engram 表参数的
`exp_avg` 平均 ~1.7e-4、`exp_avg_sq` ~2e-11；对比 `embed.weight` 是 7.1e-2 / 1.4e-8。
即表的梯度弱约 3 个数量级，且**方向互相抵消**。原因是哈希桶被大量**不相关**的
n-gram 共享：同一个桶每步收到方向相反的梯度，AdamW 的 `m/√v` 恒在 0 附近 → 行永远
不"承诺"到某个值；而单遍网文里同一 n-gram 又极少重现，行拿不到一致的目标。

**教训**：
- 哈希/查表类记忆的收益来自**上下文重现**（同一 n-gram 反复出现）或大规模预算；
  在"单遍语料 + 小模型 + 短预算"下，它只会往主干里注入噪声，**加容量 ≠ 涨点**。
  要验证收益必须造重现：多 epoch、高频模板（SFT 套话）、代码/结构化文本，或把
  训练量拉到论文同量级。单遍 Web 文本 + 8191 表 ≈ 无效。
- 把预算拉到 4 倍（2500 步 ≈ 10.2M token）、把表放大 8 倍（8191→65521）各跑一遍，
  差值仍全程在 ±0.002 内——**"表太小/碰撞太多"这个解释被证伪**，瓶颈就是"没有重现"。
  排查这类问题时，先把替代解释各做一个对照跑掉，再写结论。
- **判定"记忆模块活没活"别只看 loss**：三步走——(a) 看参数相对初始化的漂移，
  (b) 把读出门（`W_V`）置零看 logits 差异（零初始化 = 恒等，故置零即"关记忆"），
  (c) 翻优化器 state 看该参数的 `exp_avg`/`exp_avg_sq`。三者一起才能区分
  "没接上 / 接上但没学 / 学了但没用"。
- 这类"中性"结果要如实记录：它证明了恒等起点与训练稳定性（多出的参数不伤基线），
  但**不能**用来宣称特性有效——两码事，别混着写进结论。

## 22. `eval_batches` 决定评测子集——改它会让 loss 曲线整体平移

**现象**：同一初始权重、同一 holdout，`--eval-batches 20` 与 `40` 的 val_loss 差 ~0.15
（20 批 4.52 vs 38 批 4.67）。差点被误读成"这一版训练把模型练坏了"。

**机制**：`evaluate()` 每次用 `make_eval()` **重建**评测流，然后**只取前 N 批**
（`zip(range(n_batches), make_eval())`，不 shuffle、不循环）。而 holdout 是**顺序切分**的
文档，前后段难度天然不同：本机 128 篇 holdout 打包出 38 批，前 20 批均值 ~4.52、
后 18 批 ~4.83（站点/主题聚集 → 后段更难）。于是 `eval_batches` 一改，**评测集就换了**，
两条曲线不可比。顺带一个坑：样本不足时 `StopIteration` 后按**实际批数**平均，
不会报错也不会循环——所以"批次数"和 `eval_batches` 未必相等，别用错分母。

**教训**：
- 跨 run 比较**必须锁死 `eval_batches`**；已产生不同口径的曲线，先把它们对齐再下结论。
- 想覆盖整个 holdout 就把 `eval_batches` 设成 ≥ 总批数（本机这里设 100 即可取满 38 批）；
  反之小 N 的评测是**有偏**的（偏易）。
- 评测流若需要"代表性"，要么覆盖全量，要么固定种子打乱后取固定批数——不要用
  "文件顺序的前 N 段"当默认。

## 23. 结构开关也可能"改语义但不改 state_dict 键"——装错不报错，静默换架构

**现象**：把 CSA2（`csa_reuse_every`）的**默认值**从 1（全 Full）改成 2（Full/Reuse 交替）后，
`SmallLLMConfig()` 构建的模型与旧基线 checkpoint 的 `state_dict` **键名与形状完全一致**
（实测 800/800 相同），`load_state_dict(strict=True)` 照样通过——但 Reuse 层的 `w_dkv`/`w_kr`
被换成了相邻 Full 层的权重对象，层 4 的 KV 投影被层 0 覆盖。**不报错，语义已变。**

**机制**：多数结构开关（`memory_every`、`retro_every`、`hyper_streams`）会**增删模块**，
键集对不上就炸，天然安全；而 CSA2 只改**权重共享关系**，不增减键，故"装错"不会触发任何断言。
凡是"只改共享/别名"的开关都属这一类。

**教训**：
- 改这类开关的默认值前，先确认 **`state_dict().keys()` 是否不变**；不变就意味着必须靠
  **来源对齐**而非严格载入来保证正确。
- 训练脚本：显式值 > `--config-json` > checkpoint 的 `hparams.json` > （续训/迁移/SFT 载入
  则保守按旧默认，新训练才用新默认）。`--sft-init` 是 strict 载入，但同样会被这类开关骗过，
  必须一并纳入保护（见 `resolve_csa_reuse_every`）。
- 加载既有权重的一切脚本（`serve_openai`、`scan_dormancy`、`rejuvenate`、`init_memory`、
  `rft_sample`、`measure_mtp_acceptance`、`bench_offload_les`）都要先
  `sync_arch_from_checkpoint(cfg, <checkpoint 路径>)` 对齐，再套 CLI 覆盖。
- 判据：**"strict=True 通过" ≠ "架构一致"**。只改共享的开关，strict 永远通过。
- 同类的还有**改前向数学但不改键**的开关（如 `swiglu_limit`：只在专家内部 clamp 预激活，
  键名形状全不变）——同样必须靠 `sync_arch_from_checkpoint` 来源对齐，旧 run 回退到
  特性前的值（SwiGLU 限幅→0），否则新默认 10.0 会静默改掉旧 run 的前向数字。
- 路由也属这一类（`router_aux_free`/`routed_scaling_factor`/`norm_topk_prob`）——已登记进
  `config._ARCH_SWITCHES`，一侧登记即自动纳入 `sync_arch_from_checkpoint` 与训练脚本
  通用来源对齐（`resolve_arch_switches`），无需逐开关手写保护。

## 24. 续训对比时"重新加热"会掩盖真实差距——别把暂态读成"再训就补上了"

**现象**：判定"CSA2 的 +0.0126 差距是容量损失还是适配滞后"时，从两臂各自的收敛末态
（lr 已衰减到 ~0）继续训。任何非零 lr 都会把两臂一起**重新加热**（loss 4.39 → 4.59），
在这段暂态里，**差距一度缩到 0 甚至为负**（CSA2 反而更好）——很容易误读成"多训就补上了"。

**机制**：两臂不是"同等距离"地离开极小点。收敛更深（loss 更低）的那一臂，极小点更尖锐，
被同样的 lr 扰动得**更狠**（实测基线首段回落 +0.202、CSA2 +0.186），于是暂态中显得更差。
等两者都回落，差距又回来了。把 i3/i4/i5 全部评测点按 `base_loss` 排序即可看清：
**loss 越低 gap 越大**（r=−0.45），最低 loss 的点全为正、最高 loss 的点多为负。

**教训**：
- **配对续训的读数只在"loss 水平对齐"时可比**。别拿暂态里的差值为 0 当结论——先看
  "差距 vs loss 水平"的趋势，或让两臂都回到同一起点 loss 再读。
- 判定"固有容量 vs 适配滞后"的正解是**同起点 A/B**（同一 init、同预算、同 lr 曲线），
  而不是"在收敛点上再续训一段"；续训只能看**续训后**的稳态差额。
- **两个独立 lr 复现同一残差**（i4 2e-5 → +0.0052、i5 1e-5 → +0.0047）才算证据；
  单轮 +0.005 落在评测噪声（±0.01）里，不能单独下结论。

## 25. 按 |激活| 排序前先分符号区间——SwiGLU 双负会让弱激活"看起来像正极点"

**现象**：SwiGLU 中间激活 `m = silu(gate)·up`，当 `gate<0` 且 `up<0` 时两负相乘得**正**，
和"正门×正值"（+×+）混在同一个正极里。对 base 预训练权重实测（39168 个专家神经元）：
双负占**全部**正激活的 **58%**，但只占**最强 1%** 的 7.9%；而**约 6.7% 的神经元其最强
响应被双负占据**。也就是说，"按 |激活| / 峰值排序选重要单元"会把一批回声当成主特征。

**机制**：弱激活段 `gate`/`up` 符号接近随机（`m≈0` 处符号是噪声），双负占比自然趋近 50%
（实测 58%，仅略高）；真正的强响应才偏好 +×+。故**幅值越小的段，双负污染越重**。

**教训**：
- 任何"按幅值/峰值排序"的分析（重要性打分、可视化、按峰值选休眠）都要先按
  `(sign(gate), sign(up))` 拆成四段，别把双负 echo 当主特征。
- 休眠判定用的是**平均**激活（弱激活段），受双负影响小；一旦改用峰值/最强激活，
  这 6.7% 的 echo 神经元必须排除。
- 逐专家统计必须 hook 在 **MoE 输入**上重算（分组 bmm 后专家子模块 forward 不跑），
  与复壮同一坑。

## 26. 休眠阈值的"逐专家 vs 逐层"口径要写清——数值接近，概念不同

**现象**：`dormancy_masks` 文档写"阈值 = **层**均值 × rel"，实现却是逐个 key（=逐个专家）
取 `score.mean()`。实测两种口径给出的"最闲神经元比值"几乎一样（逐专家 0.29 / 逐层 0.28），
所以**结论（零休眠）不受影响**——但概念不同，不写清容易让人以为换个口径能"造出"休眠。

**教训**：
- 路由专家接收的 token 子集不同、激活尺度各异，**逐专家**比较更稳（现状实现即如此）；
  文档口径与实现必须一致。
- "数值撞巧一致"不能替代口径澄清；跨口径复算一遍再下结论，别默认两者等价。

## 27. 免辅助损失偏置别进 `state_dict`，且负载统计要"赋值"不要"累加"

**现象**：新增逐专家路由偏置 `expert_bias` 后，若 `register_buffer(..., persistent=True)`，
它会出现在 `state_dict()` 里——旧 checkpoint（无此键）严格载入直接报缺键，破坏"装载键兼容"。

**机制**：偏置是**训练期自适应状态**，不是架构权重：V4.1 的 `noaux_tc` 靠它调价均衡，但
它每步都在变、且与权重无固定对应关系。

**教训**：
- `expert_bias` 用 **非持久化 buffer**（`persistent=False`）：不进 `state_dict`、装载键兼容
  （旧 checkpoint 照常 strict 载入）；代价是**续训时偏置归零**，靠 `router_aux_free` 的
  sign 式更新在数步内重新自适应——这是"键兼容 vs 续跑精确"的取舍，本项目选键兼容。
- 负载统计（逐专家命中占比）在**前向里用赋值**保存（`self._last_load = f`），**不要累加**：
  梯度检查点会在反向**重算前向**，累加语义会把同一批负载计两次（偏置更新量翻倍）。
  赋值语义下重算写下同一个值 → 幂等。
- 偏置更新在 `optimizer.step()` 之后、每优化器步一次；用**最近一次训练前向**的负载
  （`sign` 式对噪声鲁棒），只影响选择、不进反向，因此不污染主任务梯度。

## 28. 改键的架构开关：默认关，但仍要登记进 `_ARCH_SWITCHES`（与"改语义不改键"区分对待）

**现象**：MLA 分组输出投影（`o_groups`/`o_lora_rank`）把 `w_o` 换成了 `w_o_d`/`w_o_u`——
`state_dict` 键变了。若像 1/2 号开关那样"默认开"，旧 checkpoint 一 `--resume` 就报缺键。

**机制**：开关分两类，保护手段不同：
- **改语义/共享关系、不改键**（`csa_reuse_every`、`swiglu_limit`、路由三件套）：装错**不报错**，
  只会静默换架构/改前向数字 → 必须靠 `sync_arch_from_checkpoint` 来源对齐，默认可以开；
- **改结构、改键**（`o_groups`/`o_lora_rank`、`mtp_depth`、`memory_every`、`hyper_streams` 等）：装错会
  strict 载入**大声报缺键** → 不会静默出错，但**默认必须关**（否则旧 run 无法续），
  属需迁移/重训的 opt-in。

**教训**：
- 别把两类混为一谈："默认开"只对第一类成立；第二类默认关不是保守，是**键不兼容的硬约束**。
- 第二类也**照样登记进 `_ARCH_SWITCHES`**（回退"关"）：好处是续训/装载脚本能按 hparams
  自动重建正确结构；若 checkpoint 与之不符，strict 载入报缺键（早失败），不会静默错。
- 改键的开关要配**迁移路径**（如 `migrate.group_output_projection` 用分组 SVD 把旧 `w_o`
  拆成新权重，附重构误差），否则"默认关"等于"这项技术永远用不上"。

## 29. 学习式稀疏 indexer：改的是"读哪些"而非张量形状；空池/全掩码必须双保险

**现象**：给稀疏注意力加学习式 indexer（Top-K 主 KV + 块级候选池）时，容易下意识认为
"有了 Top-K 就不用算全文分数了"，于是写成对每个查询 gather 自己那 K 个 key 的形式——
在候选集**常数规模**的实现里这是错误方向。

**机制**：本项目的稀疏路径**本就把可见 key 压到常数候选集**（sink+窗口+跨步，见
`select_keys`），再做一次 dense 的 `QK^T`。所以 indexer 的产出只能是**掩码**——
把未入选的候选列掩 `-inf`，softmax 后权重为 0，等价于"只读 Top-K"。若改成 per-query
gather，会额外物化 `(b, h, n_q, K, d)`，反而比掩码更贵。**真实加速需要 block-sparse
kernel**，我们没实现——文档必须诚实写明"这里省的是选择而非算力"。

**教训**：
- indexer 的落点是**在静态候选列上叠加掩码**（当前块的本地 SWA 列保持原因果掩码），
  不是重建 gather；单测用"开/关长序列输出不同、短序列逐位相同"锁定。
- **空池 → 全 `-inf` → NaN**：Reindex 层用"自己的池 ∩ 前层池"，两池可能不相交；
  必须对"空交集"回退到自己的池，再对"全 `-inf` 行"回退到未掩分数——**双保险**。
  （只做一层保护时，长序列 + 极端输入会偶发 NaN，且可能只在 batch>1 复现。）
- 块级候选池必须按候选的**全局位置**分块（`pos // block`），不是按候选序号：
  跨步候选会各占一块，窗口段才是连续块——"块=连续位置"才忠实。
- 打分提 **fp32**（候选数有界，不心疼），bf16 下长序列的 exp 易欠精。
- 该开关**新增参数 `w_iq`/`w_ik`（改键）** → 按 28 号教训：默认关 + 登记 `_ARCH_SWITCHES`
  + CLI 三态（`--sparse-indexer`/`--no-sparse-indexer`），旧 ckpt 来源对齐回退关。

## 30. 层间"选择通道"必须按**层号**键控，不能按执行序——否则梯度检查点静默错梯度

**现象**：CSA2 三模式（Full/Reindex/Reuse）要在**同一次前向内**把"Top-K 选择"从生产者
（Full/Reindex）传给借用者（Reindex/Reuse），于是加了一个前向内的临时通道。第一版写成
"按轮到的第几层"的列表（`items[i]` 顺序 append/覆盖）。**不报错**，loss 也正常下降，
但 `--grad-ckpt`（梯度检查点）开关下与前向的数学**不一致**。

**机制**：通道里 Reindex 层既读（用生产者的候选池）又写（把自己的新选择作为"最新"）。
按执行序键控时，重算阶段是**逆序**重放：Reindex 层的重算**先于**它的生产者，于是它读到的
是本层在**首次前向时覆盖上去**的值——池从"生产者的池"变成"自己的池"，重算出来的前向
与首次前向不同，反向传播的梯度因此是**错的**（静默、无报错、loss 曲线看不出来）。

**教训**：
- 通道按**层号**键控（`items[层号][块号]`）：每层只写自己的槽，借用者按记录的生产者层号
  （`csa_src`）去读。这样重算写入**幂等**（同输入同输出），任何层读到的都是生产者上一次
  前向写下的同值内容，与执行顺序无关。
- 凡"前向内跨层传中间量"的结构（本通道、`_last_load`、router 偏置统计）都要问一句：
  **反向重算时会读到谁写的值？** 只要存在"后面的层会覆盖前面的层"的写法就有坑。
- **回归锁**：`tests/test_csa_modes.py::test_grad_ckpt_matches_plain_grads` 直接比较
  `grad_ckpt` 开/关两次反向的梯度（同权重同数据，必须逐位接近）。只测前向是无法发现的。

## 31. 学习式 indexer 里，"打分"只进掩码 → 没有蒸馏损失就恒零梯度（假装在学）

**现象**：#5 落地分层稀疏 indexer 后，前向/反向都正常、单测全绿，但 `w_iq`/`w_ik` 的
`grad` **恒为 0**（或 `None`）——indexer 从来没在学，只是随机初始化在那里选 Top-K。

**机制**：indexer 的产物是 `topk_mask`（布尔），它只被用来给注意力掩码**填 `-inf`**；
`masked_fill`/布尔运算**不可微**，所以 KL/CE 的反向到不了 indexer 的打分器。

**教训**：
- 任何"离散选择"模块都需要**显式的训练信号**。按 DSA 的做法：让 indexer 的打分去拟合
  主注意力的分布，加一项 `KL(target ‖ softmax(indexer 分数))`，**目标 detach**（只训
  indexer，不反向拉主注意力），系数单独可调（`indexer_loss_coef`，0 = 不训）。
- KL 的 reduction 别用 `batchmean`：它只除第 0 维（batch），`(b, n_q, n_cand)` 会被
  `n_q` 放大成"看着吓人"的数百 nats。要么 `reduction="none"` 再 `.sum(-1).mean()`，
  要么先 reshape 成 `(b*n_q, -1)`。
- **硬契约单测**：`tests/test_sparse_indexer.py::test_indexer_gets_gradients_from_distillation`
  断言 `w_iq`/`w_ik` 的梯度非零（系数 0 时为零）——这是"indexer 真在学"的回归锁。
- 顺带一个配置坑：`sparse_chunk` 太大时**整个序列只有一块**，静态候选（块起点之前的
  token）数恒为 0，indexer 根本不会被调用——测试里必须把 `sparse_chunk` 调小，
  否则会误判"indexer 没生效"。

## 32. 压缩块 id 与 token 位置是**两套坐标**：混淆会静默看错历史（且可能越因果边界）

**现象**：主 KV 逐层压缩比 `compress_ratios` 里，"块 b 聚合 `[b*m, (b+1)*m)`"，代码里到处是
`blk_ids * m`（块 → token）与 `pos // m`（token → 块）两个方向。第一版把"块号"当"位置"用过：
`select_block_keys` 的 sink/stride 语义搬到块轴后，块 id 与 token 位置已经**不再相等**，
但掩码/池化/代表位置那几处看上去都"像是位置"，错了也**不报错**——只是模型看到了错的东西。

**机制**：块轴 pattern 下每个 id 覆盖 m 个 token，于是有三类混淆：

1. **因果**：块尾 `(b+1)*m-1` 必须 `< start`（查询块起点）。只夹取 `total // m`（"数据存在"）
   而忘了 `start // m`（"在查询之前"），当 `m > sparse_window` 时最后一块会**伸进查询块的未来**
   → 因果泄漏（前部输出会随未来 token 变化，单测能抓，但训练时只是"loss 莫名更好"）。
2. **代表位置**：条目的 rope 用**块尾**位置，不是块首。用块首会让条目"提前结束"，
   与本地窗口 `[start-window, start)` 之间漏掉近端 token。
3. **未入选块也要参与池化**：块是被池化成**一个**条目的，池化要读块内**全部** m 个成员；
   只读块首（把块 id 当 token）会得到一个"假条目"，且改其他成员不影响输出（看起来"稳定"）。

**教训**：
- 明确区分 **块坐标**（`blk_id`，pattern/池化/代表位置用它）与 **token 坐标**（`pos`，窗口/当前块/
  缓存行号用它），命名上带 `blk` 前缀；跨坐标的换算只允许两处：`blk*m`（块首）与 `(blk+1)*m-1`（块尾）。
- 因果夹取要**两个都写**：`n_valid = min(total // m, start // m)`，再夹 `start - window`。
- **回归锁**：`tests/test_compress_ratios.py` 里
  `test_far_block_ids_are_complete_and_causal`（块尾 < start 且 < start-window）、
  `test_far_columns_are_actually_read`（改**未入选**块的成员输出不变、改**入选**块必须变）
  ——后者专门防"把块 id 当 token 用"这类静默错误。

## 33. 借用层必须沿用**生产者**的压缩表示（m 与池化权重），否则"共用 main KV"是假的

**现象**：`compress_ratios="1,4"`（生产层 m=1、借用层 m=4）时，生产者自己的 K/V 是逐 token 的，
而借用层按 m=4 把**同一份** latent 池化成 4 块条目——两层"复用同一份 main KV"变成了
"复用同一份原始 latent 后各自解释"，`Reuse` 的语义（连表示都照抄）被破坏；
更隐蔽的是借用层的 `z_cmp` 建了却**永远拿不到梯度**（它的池化结果只影响自己的输出，
但短测试里恰好没人看），成了死参数。

**机制**：压缩是**表示层**的事，而 CSA2 的"复用"复用的是**表示**（生产者算好的 main KV 条目），
不是"原始 latent 的读取权"。所以 `mode != full` 的层必须与生产者同 m、同池化权重对象。

**教训**：
- `_link_csa_reuse` 里除了共享 `w_dkv`/`w_kr`（以及 Reindex 的 `w_ik`），还要：
  `compress_ratio = 生产者的 m`、`z_cmp = 生产者的 z_cmp`（**同一对象**）。
- 生产者 m=1（无 `z_cmp`）而借用层配置了 m>1 时，**删掉**借用层自己的 `z_cmp`
  （`del layer.attn.z_cmp`；注意 `param = None` 在 torch 里只是把值置空、`hasattr` 仍为真
  → 死参数还在，必须 `del`）。
- 回归锁：`test_borrow_layer_inherits_producer_ratio_and_weights` 断言
  `layers[2].attn.z_cmp is layers[0].attn.z_cmp`，以及 `not hasattr(..., "z_cmp")`。



## 34. SWA 环的"容量"与"位置"是两个数：按 prompt 长度建环，存储就有界不了

**现象**：层内 SWA（`swa_window>0`）第一版把"环容量"和"最后写入位置"合成一个参数传：
`_pack_swa(k, kr, v, t)` 里 `cap = window + t - 1`。看起来天经地义——"多 token 解码
需要 `window+t-1` 行"。但预填充时 `t = prompt 长度`，于是 8K prompt 直接建了一个
8192 行的环：**SWA 缓存退化成 O(L)**，"窗口定长、存储与序列长度无关"这条论文卖点
被自己写没了，而且没人会注意到——`kv_cache_bytes` 的加法项还写着 `window`。

**机制**：环里真正需要的只有"之后解码可能读到的位置" `[pos-window+1, pos+1)`，
与"这次一次喂了几个 token"无关。预填充只需要装**最后 `window` 个**（解码第一步只读这么远），
多 token 解码的 slack 是**之后**才需要的，可以由 `_grow_swa_rings` 按需 2x 扩。

**教训**：
- `_pack_swa(k, kr, v, pos_end, cap)` 把 `cap` 与 `pos_end` **拆成两个参数**：
  预填充 `pos_end=L, cap=window`；多 token 解码 `cap=window+t-1`。写错时行为"看起来正常"
  （输出对），只有显存曲线会慢慢露馅。
- 环行号一律用 `位置 % cap`（不是 `% window`）——扩容后旧槽位才还能按新模命中
  （`_grow_swa_rings` 按位置重映射就是为此）。
- 回归锁：`test_ring_is_bounded_and_grows_only_for_multi_token`（40 token 预填充后环仍是
  8 行；4 步解码才扩到 16）+ `test_kv_cache_swa_term_is_seq_independent`
  （`kv_cache_bytes` 的 L 增量里一字节 SWA 都不含）。

## 35. 层内 SWA 只活在**分块路径**里：短 prompt 走 dense 兜底就会"预填充没 SWA、解码有 SWA"

**现象**：`sparse_threshold` 以下的短序列原本走 `MLAModule.forward` 的 dense 兜底
（省掉 pattern/gather 的开销）。开了层内 SWA 后，dense 兜底**不带** SWA 列（它连
`SparseMLAModule` 的分块逻辑都不进），而解码路径（`_decode`）恒带 SWA 列——
于是同一个模型"短 prompt 预填充"与"解码续写"看到两种注意力范围，前几步就开始分叉。
更阴的是：短 prompt 恰恰是 agent 多轮会话的常态，这是主战场。

**机制**：SWA 的列在 `_run_blocks`/`_decode` 里拼进同一次 softmax，dense 兜底是另一条
完全独立的实现（`MLAModule`），没有"层内 SWA"这个概念。开关一开，两条路径的
注意力集合就不同了。

**教训**：
- `swa_window>0` 时**恒走分块路径**（和 `compress_ratio>1` 同一条处理：
  `if self.compress_ratio == 1 and self.swa is None and t <= self.sparse_threshold`），
  `sparse_threshold` 在 SWA 开启后失效。
- 顺带一个同源教训：SWA 开启后全局 pattern 的 **stride 集合依赖起点**
  （`range(0, start, stride)`），解码时 `start=total`、预填充时 `start=块起点`，
  两者取的静态列不同 → 近端 token 会同时出现在"全局列"和"SWA 列"里被**计权两次**。
  所以 `blk_start = (start // sparse_chunk) * sparse_chunk`，让解码与预填充按同一块起点取
  （多 token 一步解码只在**块对齐**时与全前向等价，单测按 `sparse_chunk` 对齐喂）。
- 回归锁：`test_short_prompt_also_uses_swa_path`（t=4、threshold=8 时环里有 4 行且
  `prefill+decode == 全前向`）+ `test_prefill_plus_decode_matches_full_forward`（块对齐）。

## 36. 共享 latent 缓冲扩容必须按**对象身份**去重，否则借用层读到旧副本

**现象**：`SessionCache.ensure_room` 逐层"容量不够就新建一个更大的缓冲、拷旧有效区"。
CSA2 的 Reindex/Reuse 层与生产者的 `buf_c`/`buf_kr` 是**同一个张量对象**（共享缓存）。
逐层各建一份以后，生产者写进自己那份新的，借用层手里还是旧副本——**从扩容那一刻起，
借用层看到的历史就冻结在扩容前**。不报错、不崩，只是回答慢慢变蠢；只有单轮长会话
（首次分配之后还要扩容）才踩得到。

**机制**：`ensure_room` 按"层"遍历、按"层"分配，而物理上缓存是**按对象**共享的。
同源问题还有：`_decode` 里 `pos` 是各层自己的张量，值相等但对象不同——所以去重键必须
是**张量对象身份**（`id(tensor)`），不是"层号"或"位置值"。

**教训**：
- 扩容分三遍：① 按 `id(t)` 汇总每块旧张量的目标容量（共享缓冲取各请求的**最大**）；
  ② 每块旧张量只新建一次；③ 回填时用 `fresh.get(id(p[0]))`，未扩容的层保持原对象。
- SWA 环是**定长**的，扩容时原样续接（`tuple(p[3:])`），绝不重建、绝不按 `pos` 改形状。
- 回归锁：`test_ensure_room_keeps_shared_buffer_identity`（扩容后借用层与生产者仍是
  **同一个** `id`，且环容量不变）。

## 37. 部分接受的投机解码与定长环不兼容：影子 token 的环行会被后来者读到

**现象**：投机解码一次并行验证 `t` 个草稿 token，主干前向会把 `t` 个 token 的 SWA K/V
**全部**写进环（`index_copy_` 按 `pos+i` 落位）；部分接受时只确认前 `j` 个，`pos` 回退到
`pos+j`。全局主 KV 没事（读位置由 `pos` 决定，超出的行不会被 gather），但**环的行号是
`位置 % cap`**：被拒草稿写下的行，其绝对位置落在窗口内、又 `< 之后某步的查询位置`，
后续解码会把它们当作真实历史读走。

**机制**：全局主 KV 是"按位置 gather"的稀疏读；环是"覆盖写 + 按位置取模"的密集结构，
两者对"写了但没确认"的容忍度不同。环没有版本号/掩码来表达"这几行是草稿"。

**教训**：
- `swa_window>0` 时 `_spec_eligible` 直接返回 `False`（先保正确性；正常生成仍走
  `_decode_step`，不受影响）。要恢复这条组合，需要给环加"有效到哪一位"的游标
  （或接受后重放被拒段），别靠"反正会被覆盖"的侥幸。
- 同样的思路适用于任何"多 token 一步写缓存 + 部分提交"的组合（块稀疏 kernel、连续批）。
- 回归锁：`test_speculative_decoding_disabled_under_swa`（开 SWA 时 `_spec_eligible` 恒 False）。

## 38. 借用层不能照抄生产者的整份 `past`：SWA 环会**别名**，两层互相覆盖

**现象**：CSA2 借用层（Reindex/Reuse）预填充后直接 `return self._out_proj(out), reuse`
——"缓存反正是共享的，原样返回最省事"。开了层内 SWA 后，`past` 元组尾部多了三个环，
于是两层拿到的是**同一份环对象**；解码时两层各自 `index_copy_` 写自己的 SWA K/V 到同一个环，
后写覆盖先写，下一层再读到的就是别人的 K/V。全前向（预填充）一切正常，
**只有增量解码**分叉——而且差得不多，不写回归测试根本看不出来。

**机制**：CSA2 共享的是**全局主 KV**（`buf_c`/`buf_kr`，以及 Reindex 的 indexer K），
而 SWA 是**每层自带**（V4.1：each layer retains its own ... SWA KV）。共享边界画错，
就把"每层自带的局部记忆"也共享了。

**教训**：
- 借用层只照抄前三个元素：`packed = (reuse[0], reuse[1], reuse[2])`，环由本层
  `_pack_swa(自己的 swa 投影)` 现建；解码路径同理（环来自 `past[3:]`，各层各的）。
- 判断"该不该共享"的口径：**这东西是生产者算出来的表示**（共享）还是**本层 hidden 的产物**（不共享）。
- 回归锁：`test_reuse_layers_carry_their_own_swa`（借用层环非空且与生产者**不是**同一对象）
  + `test_reuse_swa_decode_matches_full_forward`（回退这行修复后该测试必失败——已验证）。
## 39. 重放时线性注意力状态要**清零重建**，不能沿用缓存末态（那是重复计入）

**现象**：SWA Bounded Replay 第一版对线性注意力层（hybrid 里的
Gated-DeltaNet-lite）想"状态不可回退，那就沿用缓存里的末态"，省事且看起来
只影响"重放段"这一小段。实测（base 规模 / 64 token 会话 / `n_win=128`）：
重放后下一步 hidden 与真值差 **2.99e-1**，环差 **2.18**；而把线性状态清零后
是 **4.2e-6 / 1.3e-5**——差了四个数量级，且"无环冷启动"是 3.47。也就是说
"沿用末态"几乎和"不重建"一样糟。

**机制**：末态是**已经含过**重放段（乃至整段）贡献的递推状态。重放时逐 token
再喂一遍 = 同一批 token 被计入两次；更糟的是 `start=0` 的整段重放里，末态
还含着重放段之后的"未来"信息——这是与因果性直接矛盾的输入，不只是精度问题。
清零则恰好是论文口径："把 SWA（以及本仓的线性记忆）截断到重放段"——从段首
以零状态重新累积；`n_win ≥ 已缓长度` 时它本来就从零重建，故逐位精确。

**教训**：
- 重建"段内状态"一律从**段首的初始状态**开始（清零），然后把权威缓存当只读
  输入；`n_win < 已缓长度` 时丢掉的是段首之前的长程递推记忆——那是**有意的**
  截断，和 SWA 截断同一语义，不是 bug。
- 判断口径：重放**只允许从权威缓存里读**（全局主 KV、位置），**绝不允许写；
  也绝不允许把"末态"当起点**——两者都会把重放变成自证。
- 回归锁：`test_bounded_replay_rebuilds_hybrid_state_from_segment`（hybrid 下
  整段重放 `1e-5` 内精确）**外加对照**：手写"沿用末态"的版本误差必须大 100 倍
  ——防止有人图省事改回去。
## 40. CED 跳算的边界必须**块对齐**：否则全局 pattern 变了，末位置差 1e-1

**现象**：CED 的推理预填充只让解码器层跑尾巴，第一版把起点取成 `n_tok - 2*window`
（一个"看起来够用"的位置）。结果末位置 hidden 与全量 prefill 差 **1e-1** 量级——
不是数值噪声，是算错了东西。`swa_window=0` 时更明显：本该严格等价，却差 8e-3。

**机制**：稀疏注意力不是逐点独立的——它先按 `sparse_chunk` 把查询**分块**，再为整块
选静态列（sink/stride/窗口都以**块起点**为基准，见 pitfall 35）。跳算若把起点挪到
块中间，尾段第一块就变成 `[q_off, q_off+chunk)`，与全量的块边界错位 → 静态列集合不同
→ 末位置看到的历史不同。`swa_window>0` 时更绕：窗口列的 K/V 由窗口内各位置**自己的
hidden** 生成，"将来会被解码读到"的那 W 个环行自身也得自洽，所以还要再往前留一个 W。

**教训**：
- `q_off` 一律取 `((n_tok - 1) // sparse_chunk) * sparse_chunk`（最后一个 token 所在块的
  起点），再按窗口需求整块前推：`while n_tok - q_off < 2*swa_window: q_off -= chunk`。
- 尾段长度固定按 **2×窗口**（不是 1×）：实测 tail=2W 时末位置与环都逐位一致，
  tail=W 时差 1e-1——这条差距写进单测当对照，防止有人"优化"回 1×。
- 回归锁：`test_ced_prefill_skip_is_exact_without_swa`（块对齐后 1e-6）、
  `test_ced_prefill_skip_with_swa_replays_two_windows`（2W 精确 + 1W 必错）。

## 41. 梯度检查点下 `ced_src` 必须当**输入**传，不能靠闭包捕获

**现象**：CED 解码器层的 KV 来自编码器输出 `H_enc`。训练开梯度检查点时，首版把
`ced_src` 和 `retro_mem`/`engram_ids` 一样丢进闭包（`fn(hh)` 里直接用）。loss 正常、
训练不报错，但**编码器层的 KV 下投影梯度恒为 0**——模型看起来在训，实际只有解码器
和 MoE 在学。

**机制**：`torch.utils.checkpoint.checkpoint(fn, h)` 只把**显式传入的张量**当作可微
输入；闭包里捕获的张量在重算时被当作常量，反向不会经过它。`retro_mem`/`engram_ids`
本来就是 frozen 的（不要求梯度），所以以前放在闭包里没事；`ced_src` 是**要回传梯度**
的编码器输出，放闭包就断链。

**教训**：
- 任何"上一层输出、要回传梯度"的张量都必须列进 `checkpoint(...)` 的参数表
  （`checkpoint(fn, h, ced_src, use_reentrant=False)`，`ced_src` 为 None 时显式传 None）。
- 判断口径：**这个张量 requires_grad 吗？** 是 → 必须是 checkpoint 的输入。
- 回归锁：`test_ced_grad_ckpt_still_reaches_encoder` 同时断言"开/关梯度检查点梯度一致"
  与"编码器 `w_dkv` 梯度非零"——只比一致性抓不到"两边都断"。

## 42. CED 解码器区间混进线性层 = 跳算静默算错（必须构建期拒绝）

**现象**：CED 的收益全在"解码器层只跑尾巴"。线性注意力层（Gated-DeltaNet-lite）的
状态是**递推**的：位置 `i` 的状态依赖 `i-1`。若它落在解码器区间里，跳算前缀就等于
丢掉那段递推状态——不报错、不崩，只是输出静默偏离全量（而且偏差会随层数累积）。
更隐蔽的是"看起来还行"：随机权重下 loss 依然有限。

**机制**：CED 只改**全局注意力的 KV 来源**；SWA 和线性层的状态都必须逐位置算。
论文的架构里解码器半全是 CSA2（全注意力），所以没这个问题；本仓 1:3 hybrid 有。

**教训**：
- `ced_split_validated()` 里校验"解码器区间必须全是全注意力层"，构建期 `ValueError`；
  别指望运行时能发现（不会报错）。
- 文档要写清代价：本仓 base（`full_attn_every=4`）因此**不能开 CED**，要用
  `full_attn_every=1` 这类配置；这不是实现残缺，是架构约束。
- 顺带一条：CED 解码器层**恒为 Full**（不借前层缓存），所以 `kv_cache_bytes` 会变大
  （实测 8192 ctx 下 +38%）。"省算力"和"省显存"是两笔账，开之前先算清楚。
- 回归锁：`test_ced_requires_full_attention_decoder`（含线性层 → 抛错）、
  `test_ced_decoder_layers_are_full_mode`（解码器层 `csa_mode == "full"`）。
## 43. Sinkhorn 平衡里 `τ` 不是可选项：不屏蔽近零行，噪声会被抬成信号

**现象**：实现 Sinkhorn 更新时把"屏蔽近零行"（`ρ_i ≤ τ·ρ̄` 置 0）当成可省的细节，
`τ=0` 跑通、loss 也降。但把一行 `1e-9` 的噪声丢进去，平衡后它被放大到 **~1.16**
（行 L2 归一化把"几乎为零"抬成"单位长度"）。embedding 里天然有大量只出现一次的
低频 token（梯度极小），这些行会被逐次放大成伪信号。

**机制**：行/列交替 L2 归一化是**尺度无关**的——它只保留方向、丢弃大小。对"本来
就该是 0"的近零行，方向是纯噪声，归一化等于给它发一张满额步长。所以论文在归一化
**之前**用行范数阈值把这类行清零（`τ=1e-3`）。

**教训**：
- 平衡前先做"近零行屏蔽"，阈值用**行范数均值**的比例（`τ`），不是绝对阈值
  （不同层/步的尺度差几个数量级）。
- `ε` 只能防除零，不能防"放大噪声"——两件事别混。
- 回归锁：`test_sinkhorn_balance_masks_near_zero_rows` 同时断言
  `τ=1e-3` 时近零行为 0、`τ=0` 时**被放大**（把"为什么需要 τ"写进测试）。

## 44. 优化器分组是训练状态的一部分：换开关必须早失败，别静默丢动量

**现象**：给 Muon 加 head-wise 子组、给 embedding 加 Sinkhorn 组后，旧 `optim.pt`
里的 group 数/参数顺序对不上。若按"能载多少载多少"的宽松策略装载，AdamW 的
`load_state_dict` 会把动量错配到别的参数上——不报错，只是每条曲线的起点都悄悄变了。

**机制**：`state_dict()` 按 group 顺序存，`load_state_dict` 按顺序恢复。**分组方式
变了（开关切换）就等于参数→状态的映射变了**，而这不体现在张量形状上（很多参数
形状相同），所以静默错配是可能的。

**教训**：
- `state_dict()` 里带 `kind` 标记（`muon+headwise+sinkhorn+adamw`），装载时校验
  "当前分组"与"存盘分组"一致，不一致直接抛错并提示删 `optim.pt`（权重照常复用、
  只丢动量，重启后 warmup 很快回来）。
- 新增分组 = 新增 `kind` 变体，别只往字典里塞键而不更新标记。
- 回归锁：`test_combined_optimizer_state_roundtrip_and_mismatch`（往返成功 +
  两个方向的开关不匹配都抛错 + 非 Muon 存盘抛错）。
